# 4. 원문 전체 창 분할을 닫고, v20 금액 하한의 법 근거가 없음을 찾다

2026-09-21 밤. 목표는 Public 0.70(현재 0.6840, **+0.016 필요**).

## 1. 평가셋은 층화돼 있다 — 그런데 그게 구멍으로 이어지지는 않았다

평가 문서에 명시돼 있다: "평가 데이터는 24개 항목 **모두에 위반(=1) 사례를 포함**하므로, 특정 항목의 F1이 정의되지 않는 경우는 발생하지 않습니다." 테스트 1,853건.

자연 분포에서는 불가능한 구성이다. 무라벨 20,000건에서 v23은 6건, v5·v21은 각 27건 수준이라 1,853건을 자연 추출하면 0건이 나온다. **따라서 희소 항목이 인위적으로 채워져 있다.**

여기서 나온 가설: macro F1은 항목마다 1/24로 균등 가중하는데 우리 선택 지표(자연 20,000건 Δ양성)는 **자연 빈도로 가중**한다. v14·v17·v18을 3배 과대, v5·v21을 8배 과소, v23을 0배로 본다.

**가설은 맞았지만 찾을 수 있는 누락으로 이어지지 않았다.** 판정기와 독립인 정규식으로 전수 조사:

| 항목 | 적용 모집단(meta만) | 그물 후보 | 원문 대조 |
|---|---:|---:|---|
| v23 | **1,168** (지방+협상에의한계약) | 37 | **0/4 진짜** — 미개최·날짜없음·날짜중복 |
| v5 | **1,177** (고시금액 이상) | 1 | **0/1** — 제출서류 목록이었다 |

v5는 적용 모집단의 **89%에 소재지 문장 자체가 없다.** 자격문맥+소재지 줄이 있는 건 3건이고 판정기가 이미 2건을 잡고 있다. 09-21 낮의 "드물어서 얇은 것이지 탐지 실패가 아니다"가 재확인됐다.

**교훈: `계약방법` 필드에 '협상'은 없다.** 협상에의한계약은 `낙찰방법`에 있다(수의계약 8,961 · 협상에의한계약 4,869 · 적격심사제 3,704 · 규격가격동시입찰 2,258 · 2단계경쟁입찰 199 · 종합낙찰제 9). 게이트를 세울 때 필드를 먼저 확인할 것.

## 2. 원문 전체 창 분할 — 기각 (dev -0.0218)

09-20에 비용(prefill 2,000만·+30~45분)을 이유로 버렸고 09-21 낮에 "서버가 2배 빠르니 되살리자"고 했던 설계다. 실제 비용은 실측 13,100 tok/s로 **서버 +15~25분**이라 감당 가능했다.

`scripts/window_sweep.py`: 원문을 10k 토큰 창으로 잘라(레코드당 평균 1.57창, dev 200건 = **314창**, 로컬 생성 **2시간 4분**) 본 호출과 같은 스키마·지시문으로 창마다 추출하고 사실을 병합(불리언 OR). 전용 호출은 양쪽에 동일 적용해 본 호출만 달라지게 했다.

| | macro |
|---|---:|
| 기준(발췌) | **0.8451** |
| 창 분할 | 0.8233 (**-0.0218**) |
| 발췌+창 사실합집합 | 0.8451 (**모든 칸이 기준과 동일**) |

dev가 in-sample이라 불리하다는 반론이 가능하지만 **이번엔 오탐 증가가 아니라 정탐 손실**이다: v1 4→2, v11 4→3, v13 6→5, v19 5→4. 원문을 더 읽혔는데 탐지가 줄었다.

`ITEM_SOURCE`를 통째로 한 모드로 고정해 재면 더 분명하다:

| 모드 | 발췌 | 발췌+창 |
|---|---:|---:|
| rx | 0.7384 | 0.7384 (구조상 불변) |
| llm | 0.6879 | **0.6623** |
| or | 0.6898 | **0.6646** |
| and | 0.6999 | 0.6986 |

**전 모드 악화.** 창이 새 사실을 못 찾은 게 아니다 — 대기업_참여제한_문구 **+25**, 특정모델_지정 **+17**, 지역제한 **+16**, 확약서 +10, 제안서_마감일 33건(창에만). 동시에 발췌가 갖고 있던 것을 잃었다(확약서 -13, 대기업 -11, 실적제한 -7). **순증한 사실이 판정을 전혀 개선하지 않았다는 것은 새로 찾은 것이 대부분 오탐이라는 뜻이다** — 그물이 일부러 뺀 51%(제출서류 목록·일반 유의사항·계약 일반조건)의 상투문을 제한으로 읽는다.

> **발췌 정규식 그물은 비용 절감책이 아니라 신호 농축기다.**
> "LLM이 원문의 49%만 본다"는 것은 결함이 아니라 설계다. 컨텍스트를 늘리는 방향의 제안은 이 측정으로 기각한다.

09-20의 그물 확장(35%→48%, dev -0.0063)과 09-21 S1의 "제출서류 그룹이 본 호출을 오염시킨다"와 같은 현상이다. 발췌 커버리지는 dev 중앙값 **49.2%**다 — 09-19의 35%는 낡은 수치이고 현재 후보에는 넓힌 그물이 이미 들어가 있다.

**부수 확인:** `ITEM_SOURCE`가 24개 중 16개를 `rx`로 고정하므로 본 호출 LLM 사실은 **8개 항목**(v1·v9·v11·v13·v15·v19 llm, v10 and, v23 or)에서만 판정에 닿는다. 본 호출 품질 개선의 사정권이 그만큼 좁다.

**구현 함정:** `build_json_schema_logits_processor`는 **상태 객체라 호출마다 새로 만들어야 한다.** 루프 밖에서 한 번만 만들었더니 3창 중 2창이 `LLGuidance matcher error: parser stopped in consume_token`으로 실패했다. 고친 뒤 314/314 유효.

## 3. 항목별 정밀도 예산 — 억제할 곳이 없다

손라벨 220쌍을 현재 후보의 예측과 교집합해 다시 쟀다. **낡은 쌍 55개**(이전 후보가 켰다 끈 것)를 빼지 않으면 정밀도가 0.591로 잘못 나온다. 제대로 재면 165쌍 중 124 = **0.752**.

F1/2 문턱은 macro 평균이 아니라 **항목 자신의 F1**에서 나온다:

| 판정 | 항목 |
|---|---|
| **억제가 이득 (정밀도 < 문턱)** | **0개** |
| 확대 여지 (11개) | v18 0.96/0.40 · v14 1.00/0.44 · v2 1.00/0.47 · v16 0.88/0.39 · v7 0.92/0.47 · v9 0.82/0.39 · v10 0.62/0.23 · v13 0.71/0.40 · v17 0.73/0.39 · v20 0.78/0.46 · v1 0.60/0.33 |

**파이프라인은 전 항목에서 균일하게 과보수적이다.** 그리고 24개 중 **20개는 전역 0.342보다 문턱이 높다** — 09-21 낮의 전방위 재현율 확대는 v10·v11·v1·v24 네 항목에만 맞는 처방이었다.

## 4. F1/2는 부호만 알려주고 크기는 알려주지 않는다

"정밀도 0.34만 넘으면 채택"을 **전략**으로 쓰면 안 된다. +0.016에 필요한 양이 정밀도에 따라 폭발한다:

| 새 탐지 정밀도 | 테스트 양성 | **20,000 환산** |
|---:|---:|---:|
| 1.00 | 43 | 460 |
| 0.85 | 55 | **595** (recall_first가 +457) |
| 0.70 | 78 | 845 |
| 0.50 | 177 | **1,910** |
| 0.40 | 484 | 5,220 |

문턱 바로 위의 탐지는 건당 이득이 0에 수렴한다. **0.70은 정밀도 0.85로 +600건이거나 항목 하나를 통째로 끌어올리는 것, 둘 중 하나다.**

## 5. v20 금액 하한은 법 근거가 없다 (다음 후보)

`scripts/gate_ablation.py`를 현재 후보 기준으로 갱신해 15개 억제 게이트를 3,000건에 돌렸다. 대부분은 법 근거가 확인된 것(수의계약 게이트·우선조달 예외 면책·제7조 경쟁입찰 예외)이라 손대면 안 되는데, **하나가 출처 불명이다.**

```python
v["v20"] = int(is_software(rec) and priced and p >= ONE_HUNDRED_MILLION and not facts.get("대기업_참여제한_문구"))
```

법령패키지 원문 — `중소 소프트웨어사업자의 사업 참여 지원에 관한 지침` **제3조②**:

> 소프트웨어사업을 발주하는 경우 입찰공고문 또는 제안요청서에 대기업 참여제한 하한제도 **적용 여부**(적용 근거 포함)를 명시하여야 한다.

**"적용한다"가 아니라 "적용 여부"다.** 적용하지 않는 경우에도 그 사실을 적어야 하므로 금액 하한이 붙을 자리가 없다. 오히려 소액 SW사업일수록 별표1의 하한(20억/40억/80억)이 실제로 대기업을 배제하므로 명시 의무가 더 무겁다. 09-19에 "v20은 **상한**이 없다"를 닫았는데, **하한도 마찬가지**였다.

| | |
|---|---|
| 무라벨 20,000 v20 양성 | **185 → 623 (+438)** |
| ΔPublic 추정 (p=0.85) | **+0.0127** |
| 채택 문턱 | **0.455** (v20 dev F1 0.909 ÷ 2) |
| dev | 0.909 → 0.769 (오탐 +2 · **정탐 +0**) |

dev가 내려가지만 dev v20은 **5/1/0으로 누락이 0건**이라 재현율 확대가 오탐으로만 보이는 구조다 — `recall_first`(dev -0.0059인데 Public +0.0123)와 정확히 같다.

**미확정 이유: `is_software`가 헐겁다.** 면허업종제한목록에 소프트웨어사업자가 한 줄만 있어도 발동해서 **배수관로 관급자재·전자책 구매·직무연수·3D 스캐닝**까지 잡힌다. 부분집합으로 정밀도를 높이려 했으나 **가설이 반대로 나왔다**:

| 부분집합 | 건수 | 표본 인상 |
|---|---:|---|
| 면허업종에 SW + 일반용역 | 216 | 직무연수·홍보용역·3D스캐닝 등 **비SW 다수** |
| 본문에만 SW | 92 | 학사행정시스템·버스정보시스템·전산시스템 유지보수 — **오히려 진짜 SW** |

**면허업종 필드는 약한 증거다.** 목적물 기준 판단이 필요하다.

→ 손라벨 시트 준비: **`labels/train20k_v20_lowbound.csv`** (438건 중 무작위 40건, 표준오차 ±0.08). 정밀도 0.455 초과면 채택, 미달이면 `is_software`를 목적물 기준으로 조여 재측정.

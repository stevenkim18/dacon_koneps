# dev 재분석: v22/v23 적용 조건 오표기, v13 대량 오탐 원인, 근거 문구 희소성

## 1. 계기

attachment_excerpt(v1)를 검증하던 중 v13 오탐(fp 23~24건)과 v22 소폭 하락(-0.238)이 남아 있었다. "다시 처음부터" dev.jsonl·dev_labels.csv를 직접 재검토해 원인을 찾는다(모델 없는 순수 데이터/문자열 분석, scripts/analyze_dev.py가 이미 다룬 범위를 넘어서는 부분 위주).

## 2. 발견 A — v22/v23의 적용 조건이 항목표.json 항목명에서 잘못 표기됨

`항목표.json`은 v22를 `"현장설명회 참석업체 (자격으로 제한 여부) * 계약방법 협상만 적용"`, v23을 `"* 계약방법 협상 + 계약법 지방만 적용"`이라고 적어 두었다. 그런데 dev 200건의 `meta.계약방법` 분포는 다음과 같다.

| 계약방법 | 건수 |
|---|---:|
| 제한경쟁 | 135 |
| 수의계약 | 35 |
| 일반경쟁 | 30 |

**'협상'이라는 값 자체가 존재하지 않는다.** 실제 v22·v23 양성 10건의 메타를 직접 찍어보면:

```
v22 양성 5건: 전부 낙찰방법='협상에의한계약'
v23 양성 5건: 전부 낙찰방법='협상에의한계약' + 적용계약법='지방계약법'
```

즉 "협상"은 `계약방법`이 아니라 `낙찰방법` 필드의 값이다. dev 200건 정답 전수로 역방향 검증(양성인데 조건을 벗어난 예외가 있는지)해도 **예외 0건**이었다.

→ 이 조건을 벗어나면 위반이 아니라고 **확정**할 수 있다(필요조건이 100% 성립). `postprocess()`에 결정론적 규칙으로 추가해도 재현율 손실이 없다: `낙찰방법≠'협상에의한계약'`이면 v22를 0으로, 추가로 `적용계약법≠'지방계약법'`이면 v23도 0으로 강제.

## 3. 발견 B — v13 대량 오탐의 원인은 "적용 전제 조건 누락"

09-17 첫 번째 MLX 실행에서 v13(중기간 경쟁제품 소기업·소상공인 제한)이 baseline·attach 모두 fp 23~24건이었다. 오탐 6건을 직접 읽어보니 **전부 실제로 "소기업·소상공인 확인서 소지자에 한함" 같은 문구가 진짜 있었다.** 모델의 문자열 인식 자체는 정확했다 — 그런데 v13은 그 문구만으로 성립하지 않는다. 항목 정의상 **그 품목이 중기부 고시(제공된 `법령패키지/중기부고시/중기부고시_경쟁제품_세부품명.csv`, 615개 세부품명번호)에 등재된 "중기간 경쟁제품"일 때만** 위반이다 — 아니면 일반물품 조항(v14/v15/v17, 판로지원법상 합법적 예외 있음)의 영역이라 같은 문구라도 위반이 아닐 수 있다.

`meta.세부품명번호목록`을 이 CSV와 대조한 결과:

| 구분 | 세부품명번호 없음(None) | 목록에 있음(진짜 중기간경쟁제품) | 목록에 없음(오판정) |
|---|---:|---:|---:|
| v13 진짜 양성 6건 | 6 | 0 | 0 |
| v13 오탐 24건(baseline) | 11 | 0 | 13 |
| v13 오탐 23건(attach) | 11 | 0 | 12 |

세부품명번호가 있는 오탐은 **100%** 목록 밖 품목이었고, 진짜 양성은 전부 세부품명번호가 메타에 없었다(코드가 없다는 것 자체가 목록 매칭을 막지 않는다는 뜻이자, 이 규칙이 진짜 양성을 지울 위험이 없다는 뜻이기도 하다).

→ 세부품명번호가 있고 목록에 없으면 v13을 0으로 강제(위험 없음, dev 기준 fp의 약 50%를 제거). 코드가 없는 나머지 11건은 이 규칙으로 못 걸러 별도 프롬프트 개선이 필요하다(다음 실험 후보로 남김).

**주의**: 같은 논리를 v10/v11(중기간 경쟁제품 관련 부재탐지)이나 v12(일반제품 직생 제한)에 그대로 확장하면 안 된다. v12 양성 사례는 오히려 **세부품명번호가 목록에 없는 경우**(일반제품이므로 당연함)였고, v10/v11 양성도 전부 세부품명번호가 None이라 이 규칙으로 걸러지지 않는 것과 별개로, "목록 밖이면 0" 규칙을 걸면 v12는 정반대 방향이라 오적용된다. 이번에는 v13에만 좁게 적용했다.

## 4. 발견 C — 근거 문구는 대부분 항목에서 애초에 희소하다

24개 항목(부재탐지 5개 제외 19개) 중 gold 근거(`e`)가 채워진 비율을 dev 200건 전수로 계산:

| 항목 | 근거 있음 | 근거 없음(빈칸) |
|---|---:|---:|
| v9 | 3/6 | 3/6 |
| v22 | 5/5(문서 위치 혼합 포함) | 0/5 |
| v23 | 5/5 | 0/5 |
| v2, v3, v7 | 전건 | 0 |
| v1, v5, v6, v8, v12, v13, v14, v15, v17, v19, v21, v24 | 10~30% | **70~90%** |

**v9만 유일하게 근거가 첨부(규격서)에 몰려 있고**, 대부분의 다른 항목은 양성이어도 정답 근거 칸이 대부분 비어 있다. 즉 "근거 보존율"은 v9류 소수 항목에서만 의미 있는 대리 지표이고, 09-16 balanced_context가 노렸던 "근거를 더 많이 보존하면 F1이 오른다"는 가정은 애초에 대부분 항목에 적용되지 않는 전제였다 — attachment_excerpt가 v9에서만 크게 개선되고 다른 항목은 그대로인 것과 정합적이다.

## 5. 구현 및 재검증

`submissions/20260916_attachment_excerpt/script.py`의 `postprocess()`에 두 규칙을 추가했다(코드는 파일 내 주석 참고, `_gate_v22`/`_gate_v23`/`load_sme_competitive_codes`).

재검증은 이전 MLX 실행(v1, 128건)과 **완전히 동일한 프롬프트·seed·temperature=0**이라 모델 생성 텍스트가 그대로이므로, 40분짜리 재추론 대신 저장된 원문 출력(`runs/mlx/attach_outputs.jsonl`)에 새 `postprocess()`만 다시 적용해 즉시 확인했다(prompt/context 구성 코드는 이번에 전혀 바뀌지 않았으므로 이 방법이 재추론과 동일한 결과를 낸다).

| 항목 | pos | baseline | attach(v1) | attach+게이트(v2) |
|---|---:|---|---|---|
| v13 | 6 | 0.000 (fp=24) | 0.067 (fp=23) | **0.111 (fp=11)** |
| v22 | 5 | 0.571 | 0.333 | 0.333(변화 없음 — 이 표본엔 게이트 위반 사례가 없었음) |
| v23 | 5 | 0.000 | 0.000 | 0.000(변화 없음, 동일 이유) |

**macro F1: baseline 0.1405 → attach(v1) 0.1735 → attach+게이트(v2) 0.1753** (v1 대비 +0.0018, baseline 대비 +0.0348)

v13 fp가 23→11(약 절반)으로 줄어 예측대로 작동했다. v22·v23 게이트는 이번 128건 표본에서는 모델이 애초에 그 조건을 어긴 적이 없어 국지적으로는 효과가 0이지만, 서버 평가셋 1,853건 전체에서는 안전망으로 계속 유효하다(재현율을 해칠 수 없는 규칙이므로 손해가 없다).

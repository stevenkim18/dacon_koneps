# 로컬 MLX 추론 확보 + attachment_excerpt 후보 항목별 F1 비교

## 1. 목적

두 가지를 동시에 확보한다.

1. 지금까지 없었던 **로컬 실제 Gemma 4 추론 파이프라인**. 이전에는 "모델 없는 대리 지표"(근거 보존율, 키워드 잔존율)만으로 09-16 `balanced_context`를 제출했고, 결과적으로 대리 지표는 전부 개선됐는데 리더보드 F1은 -34% 하락했다. 항목별 F1을 리더보드 제출(하루 1회) 없이 볼 수 있어야 실험 속도를 올릴 수 있다.
2. 09-16 study log에 적어 둔 **다음 실험**: 원래 시스템 프롬프트·공고문 4,000자는 그대로 두고, 첨부 의존 항목(v9·v19·v22·v23 등)을 위한 짧은 발췌(~1,000자)만 추가하는 단일 변수 실험.

## 2. 로컬 추론 환경

- 대회 고정 모델 `google/gemma-4-26B-A4B-it`은 2026-04-03에 실제 공개된 모델이었다(MoE, 총 26B·활성 4B). `mlx-community/gemma-4-26b-a4b-it-4bit`로 이미 MLX 4bit 변환본이 배포되어 있어, **다른 세대 모델로 대체하지 않고 같은 모델 계열**로 로컬 검증이 가능했다.
- `.venv`에 `mlx-vlm==0.7.1` 설치, 모델 가중치(~14GB)를 `models/gemma-4-26b-a4b-it-4bit`에 다운로드.
- `mlx-vlm`은 `llguidance` 기반 JSON 스키마 강제 디코딩(`logits_processors`)을 지원한다. `정답스키마_디코딩.json`을 그대로 사용해 서버의 vLLM `StructuredOutputsParams`와 같은 방식으로 구조화 출력을 강제했다.
- `scripts/mlx_eval_dev.py` 신규 작성: 평가할 `script.py` 경로만 받아 그 파일의 `build_system_prompt`·`build_messages`·`fit_to_budget`·`parse_judgment`·`postprocess`를 **그대로 재사용**한다(별도로 로직을 다시 구현하지 않음 — 실제 제출 코드와 프롬프트·파싱·후처리가 100% 동일하다는 뜻). MLX로 생성한 뒤 `dev_labels.csv`와 대조해 항목별 precision/recall/F1과 macro F1을 계산한다.

### 서버와의 차이(주의)

- 서버: vLLM + `int8_per_channel_weight_only` 양자화. 로컬: mlx-vlm + 4bit 양자화. **양자화가 달라 점수가 그대로 일치하지 않는다.** (대회 토크보드도 "로컬 MLX 테스트는 가능하나 로컬과 서버의 점수·출력이 다를 수 있다"고 안내한다.)
- 따라서 이 로컬 결과는 **방향성 판단용 대리 지표**이며, 리더보드 점수를 예측하는 용도가 아니다. 다만 이전의 "근거 보존율" 같은 모델 없는 지표보다는 실제 모델 판정에 훨씬 가깝다.

## 3. 평가 표본

dev 200건을 전부 돌리면 건당 17~20초 기준으로도 1시간 가까이 걸리고, 두 변형(베이스라인/후보)을 비교하려면 그 두 배가 든다. 24개 항목의 양성 사례를 빠짐없이 보면서 시간을 줄이기 위해 다음과 같이 층화 표집했다.

- 위반 라벨이 하나라도 있는 공고 **88건 전부**
- 정상 공고 중 무작위 **40건** (seed=20260826)
- 합계 **128건** — 24개 항목의 양성 셀을 전부 포함하면서(recall 측정 가능) 오탐 신호도 일부 확인 가능

**표본이 위반 비중을 인위적으로 높였으므로, 여기서 나온 macro F1은 dev 200건 전체나 실제 리더보드 macro F1과 절대값으로 비교할 수 없다.** 같은 표본으로 baseline과 후보를 **상대 비교**하는 용도로만 쓴다.

## 4. attachment_excerpt 후보 (단일 변수)

`submissions/20260916_attachment_excerpt/script.py` — 공식 베이스라인을 그대로 복사한 뒤 다음만 추가했다.

- `attachment_excerpts()` 함수: 첨부문서(규격서·과업지시서·제안요청서·예외공표서)에서 `모델명·규격·제품명·확약서·현장설명회·직접생산·소프트웨어사업자·중소기업자간 경쟁제품` 앵커 키워드와 영문+숫자 제품 코드 패턴 주변만 짧게 발췌. 앵커가 없는 문서는 서두 200자만 표시.
- `build_user_prompt()`에 한 줄 추가: 기존 `build_context(rec, max_chars)`(공고문, 4,000자 예산 — **베이스라인과 완전히 동일**) 뒤에 `attachment_excerpts(rec, budget=max_chars//4)`(기본 1,000자)를 덧붙인다. `fit_to_budget`이 토큰 초과로 `max_chars`를 줄이면 첨부 예산도 같은 비율로 줄어든다.
- 시스템 프롬프트, 법령 조문명 추가, "불확실하면 0" 지시, 모델 호출 방식, JSON 파싱·근거 검증·CSV 저장·자가검증 — **전부 베이스라인 그대로**, 변경 없음.

09-16 `balanced_context`는 문서 예산 확대·법령 조문명 추가·보수적 0 지시·발췌 방식을 한 번에 7가지 바꿔 원인을 분리할 수 없었다. 이번에는 정확히 이 한 가지만 바뀐다.

## 6. 해석

- **v9(과업지시서 특정 모델명 명시)가 recall 0% → 83%로 뛰었다.** 이 항목은 09-16 dev 분석에서 이미 "규격서·과업지시서가 4,000자 예산에서 통째로 잘려 확인 가능한 근거 3개가 전부 사라진다"고 지목했던 바로 그 항목이다. 원인을 정확히 짚고 그것만 고쳤더니 그 항목에서 정확히 개선이 났다 — 우연이 아니라 인과관계로 설명된다.
  - 근거 문구 품질도 직접 확인했다. 예) `PPS-DEV-09`: 정답 `Chipset: GB10 Grace Blackwell Superchip` ↔ 예측 동일 문자열 완전 일치. `PPS-DEV-12`: 정답 `제조사·모델명 : 아크론브라스(Akron Brass) 터보젯(TurboJet)...` ↔ 예측 동일. 발췌가 정확한 원문을 노출했고 모델이 그것을 그대로 인용했다.
- v3(실적제한 1배수)·v5(고시금액 이상 지역제한)도 소폭 개선. v7은 0 → 0.222로 새로 일부 잡기 시작.
- **v22가 0.571 → 0.333으로 하락**(recall 0.40→0.20, 양성 5건 중 1건 차이). precision은 1.0으로 유지되어 오탐이 는 게 아니라 놓친 게 하나 늘었다. 양성이 5건뿐이라 1건의 차이가 F1을 크게 흔든다 — 표본이 작아 노이즈일 가능성이 높지만, 첨부 발췌가 현장설명회 관련 문맥을 오히려 가리거나 잘랐을 가능성도 배제할 수 없다. 실제 제출 결과(또는 전체 200건 재평가)로 재확인이 필요하다.
- v19도 소폭 하락(정밀도 1.0→0.5, 재현율은 동일) — 역시 양성 6건 중 노이즈 범위.
- **v13은 baseline·후보 모두 대량 오탐**(fp=23~24, 양성은 6건뿐)이다. 이번 실험과 무관하게 시스템 프롬프트나 항목 정의 자체에서 v13(중기간 경쟁제품 소기업·소상공인 제한)을 모델이 과도하게 위반으로 판정하는 것으로 보인다. **별도로 조사가 필요한 이슈로 남긴다.**
- 09-16 `balanced_context`처럼 전면적인 붕괴는 없었다. 변경 범위를 좁히고 원인을 하나로 유지한 결과, 개선(v9·v7·v3·v5)이 하락(v22·v19)보다 크고 넓게 나타났다.

## 7. 한계

1. 128건은 위반 비중을 인위적으로 높인 표본이라 **절대 macro F1을 리더보드와 비교할 수 없다.** 상대 비교(같은 표본, 같은 모델, 문맥 구성만 다름)만 유효하다.
2. 로컬(mlx-vlm + 4bit)과 서버(vLLM + int8)는 양자화가 달라 **출력이 그대로 일치하지 않는다.** 방향성 신호로만 사용한다.
3. v13처럼 이번 실험과 무관해 보이는 기존 결함이 섞여 있어, 이번 변경만으로 설명되지 않는 변동이 일부 있을 수 있다.
4. v22·v23은 양성 5건뿐이라 표본을 넓히기 전까지는 하락 여부를 확정할 수 없다.

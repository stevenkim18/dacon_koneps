# 2026-09-20 ② 2시간 예산은 70%가 비어 있고, 채택 규칙이 점수를 깎고 있었다

사용자가 지적한 관점: **실행 제한이 2시간이고, 그 안에서는 점수를 올리는 데 얼마든지 써도 된다.**
이 관점에서 파이프라인을 다시 재면 세 가지가 나온다 — 자원의 70%가 놀고 있고, LLM은 원문의 1/3만 보고 있고,
채택 규칙(정밀도가 떨어지면 기각)이 **F1 수식상 점수가 오르는 변경을 계속 버리고 있었다.**

## 3. 계산 — F1 비대칭: 새 탐지는 정밀도 0.34만 넘으면 점수가 오른다

F1 = 2·TP / (2·TP + FP + FN). 여기에 새 탐지 k건을 더한다(t건은 놓쳤던 정탐, f건은 오탐, k = t + f).

    A = 2·TP,  B = 2·TP + FP + FN,  F1 = A/B
    새 F1 = (A + 2t) / (B + t + f)
    (A+2t)/(B+t+f) > A/B  ⟺  2tB > A(t+f)  ⟺  t/(t+f) > A/(2B) = F1/2

**새로 켠 탐지의 정밀도가 `현재 F1 / 2`를 넘으면 F1은 올라간다.**
현재 Public 0.6717 → 문턱은 **0.336**. 즉 **3건 중 1건만 맞아도 이득**이다.
반대 방향도 같다 — 양성을 취소하는 변경(게이트·거부권)은 **취소 집합의 정밀도가 0.336 미만일 때만** 이득이다.

이 식으로 09-19~20 결과가 설명된다.

| | 무라벨 정밀도 | 20,000건 양성 | Public |
|---|---:|---:|---:|
| sme_recall_reviewed (기준) | 0.770 | 4,669 | **0.67168** |
| detection_fixes | 0.796 (↑) | 4,580 (**−89**) | 0.66881 (**↓**) |

정밀도 0.77~0.80인 집합에서 89건을 지웠다. 그 집합의 정밀도가 0.336보다 훨씬 높으니 **F1은 내려가는 것이 정상이다.**
`docs/05_study_log/20260919/2`에서 "교차검증은 오르지만 무라벨 정밀도가 0.765 → 0.750으로 떨어져 기각"한 v10 `uninformed` 변형도 같은 이유로 **잘못 기각했을 가능성이 높다.**

> **채택 규칙 교체:** "정밀도가 떨어지면 기각"을 버린다.
> 새 탐지는 **정밀도 > 0.34**면 채택, 양성 취소는 **취소 집합 정밀도 < 0.34**일 때만 채택.
> 항목별로는 문턱이 그 항목 F1/2다(약한 항목은 문턱이 더 낮아 넓히는 쪽이 더 유리하다).

## 4. 추정 — 병목은 정밀도가 아니라 재현율이다

무라벨 250건 실측 정밀도 0.796. Public macro F1 0.6717. F1 = 2PR/(P+R)에 넣으면

    0.6717 = 2 × 0.80 × R / (0.80 + R)  →  R ≈ 0.58

거친 추정이다(항목별 macro F1과 쌍 단위 micro 정밀도를 섞었고, 평가셋은 무라벨보다 위반이 많이 섞여 있다 —
`docs/05_study_log/20260917/5`). 그래도 방향은 분명하다: **위반의 약 40%를 놓치고 있다.**
그리고 `labels/train500_audit.csv`의 122쌍은 전부 "우리가 양성이라 한 쌍"이라 **누락은 한 번도 측정한 적이 없다.**

**결론: 남은 84분은 전부 재현율에 써야 한다.** 정밀도 보정은 마지막에 아주 보수적으로만.

## 5. 설계 — 84분을 어디에 쓰는가

### 비용 구조 (역산)

현재 35분 47초 ≈ 모델 로드 ~5분 + 추론 ~30분 = prefill 6.9M + decode 약 1.3M.
→ 대략 prefill **8k tok/s**, decode **1.4k tok/s**(배치 집계). 이 값은 추정이므로 런타임에 실측해 보정한다(S0).

| 단계 | 추가 비용 | 누적 추정 |
|---|---|---:|
| 현재 | — | 36분 |
| S1 전체 원문 투입 (prefill 6.9M → 20M) | +1,600s | **~63분** |
| S2 항목별 질문 4~6개 (프리픽스 캐시 공유 → suffix prefill + decode만) | +600~900s | **~75분** |
| S3 핵심 질문 n=3 투표 (decode만) | +250s | **~79분** |
| S5 부재탐지 전수 재확인 (짧은 질문) | +200s | **~83분** |
| S7 양성 셀 검증 (약 425셀) | +60s | **~84분** |

여유 36분. **핵심은 S2가 거의 공짜라는 점이다** — 문서를 프롬프트 앞에, 질문을 뒤에 두면 같은 문서의 K개 질문이
vLLM 프리픽스 캐시를 공유해 문서 prefill을 한 번만 낸다. 지금은 순서가 거꾸로다(거대한 SYSTEM_PROMPT가 앞).

KV 용량 계산 (`config.json` 실측): 30층 중 **5층만 full attention**, 25층은 sliding window 1024.
→ 토큰당 전역 KV = 5층 × 8 kv헤드 × 256 head_dim × 2(K,V) × 2바이트 = **40KB/토큰**, sliding은 시퀀스당 **200MB 고정**.
10k 토큰 공고 하나 ≈ 600MB. 가용 KV 약 15GB → 동시 **~25건**. `kv_cache_dtype="fp8"`로 2배.
→ **공고를 8~16건 묶음으로 처리**하고 묶음 안에서 질문을 팬아웃한다(캐시 축출 방지).

### 5-1. 실측으로 수정한 설계 — 창 분할을 버렸다

위 표를 짜고 나서 "상한만 풀면 얼마나 더 보이는가"를 실제로 쟀다. **예산 상한을 완전히 없애도 원문의 34%(중앙값)뿐이다.**

| | 원문 대비 투입(중앙값) |
|---|---:|
| 09-19 (그룹당 900자 상한) | 35% |
| 상한만 제거 | 34%* |
| 그물 2개 추가 + 그룹별 예산(구현본) | **48%** (p90 74%) |

\* 상한 제거는 참가자격 그룹에서 중앙값 +621자를 더 얻지만 전체 비율은 거의 그대로다.
**상한이 아니라 정규식 그물 자체가 천장이었다.** 13개 그물이 걸러 내는 줄이 원문의 1/3밖에 안 된다.

그래서 문서를 10k 토큰 창으로 쪼개 전부 읽히는 설계(prefill 2,000만 토큰, +30~45분)는 **버렸다.** 대신

1. 그물을 넓히고(과업내용·제출서류 2개 추가, 기존 13개 어휘 확장) 그룹별 예산을 주고,
   예산을 넘겨도 모든 문서를 끝까지 스캔한 뒤 **앞뒤를 번갈아 남긴다**(`_fit_pieces`).
2. 9개 항목을 좌우하는 두 사실만 묻는 **전용 호출**을 추가한다 — 자격·기업규모·직생·확인서 어휘로
   문서 전체를 훑은 5,200자 문맥 + 법 조문.

제한의 법률 용어는 정해져 있어서(중소기업/소기업/소상공인/중기업) **전용 호출의 그물이 놓치는 제한 문장은 사실상 없다.**
그래서 이 두 사실에 대해서는 창 분할과 같은 커버리지를 1/3 비용으로 얻는다.

측정한 비용(dev 200건, 서버와 같은 Gemma 토크나이저):

| 호출 | 프롬프트 토큰(평균) | 1,853건 prefill |
|---|---:|---:|
| 본 호출 09-19 | 3,253 | 6.0M |
| 본 호출 09-21 | 4,882 | 9.0M |
| 전용 호출 09-21 | ~3,300 | 6.1M |
| 품목·모델명(불변) | — | 1.7M |
| **합계 09-21** | | **16.8M (09-19의 2.2배)** |

역산 처리율(prefill 8k/s · decode 1.4k/s)로 추정 **서버 55분 + 모델 로드 5분 ≈ 60분**. 예산 100분 안에 40분 여유.

### S0. 시간 관리자 (먼저 만든다, 필수)

2시간 초과는 제출 오류이고 **일일 제출 횟수를 소모한다.** 예산을 아끼는 게 아니라 **안전하게 다 쓰기 위한** 장치다.

- 하드 예산 **100분**. 단계 진입 전마다 남은 시간 확인.
- 첫 묶음(예: 32건)에서 **실측 처리율**을 재고 전체 소요를 외삽 → 초과 예상 시 뒤 단계를 자동 생략하거나 창 수를 줄인다.
- **S1이 끝나면 즉시 `submission.csv`를 쓴다.** 이후 단계는 매번 덮어쓴다 → 중간에 끊겨도 유효한 제출이 남는다.
- 단계별 소요를 stderr에 찍어 다음 제출의 예산 계획 근거로 남긴다.

### S1. 원문 전체 투입

- 문서를 **10k 토큰 창 + 500토큰 겹침**으로 분할, 창마다 같은 추출 호출 → 사실 병합.
  (`max_model_len=32768` 한 방에 넣는 대안보다 KV가 안전하고 배치 효율이 좋다.)
- 병합 규칙: 불리언은 **근거 인용이 원문 부분문자열인 것만** OR, 수준(기업규모)은 근거가 있는 것 중 엄격한 쪽, 금액은 자격 문장 기준.
- 이것만으로는 18개 항목이 `ITEM_SOURCE="rx"`라 점수가 거의 안 움직인다 → **S2와 같이 가야 의미가 있다.**

### S2. 문서 프리픽스 + 항목별 전용 질문 (필드 간섭 제거)

29필드 omnibus 1회를 **4~6개 클러스터 질문**으로 쪼갠다.

| 클러스터 | 묻는 사실 | 좌우하는 항목 |
|---|---|---|
| A 기업규모·직생·우선조달예외 | 제한 수준, 직생확인 요구, 제2조의3 예외 기재 | **v10~v18 (9개)** |
| B 실적 | 실적제한 유무, 요구금액, 공공 한정 | v2·v3·v4·v8 |
| C 지역 | 제한 유무, 시도/시군구, 시도 목록 | v5·v6·v7·v8 |
| D 품목 세부품명 | 계약목적물 세부품명번호 + 고시 특이사항 조건 | v10~v18 공통 입력 |
| E 모델명·확약서 | 특정 모델 지정, 확약서 입찰 시 제출 | v9·v19 |
| F 설명회·공동수급·SW·메타대조 | 설명회 참석 강제·일자, 최소지분율, 대기업 제한 명시, 공고서 기재값 | v20~v24 |

근거: 09-20에 **본 호출에 필드 하나(`시설인력_보유제한`)를 더했더니 v1 0.667 → 0.218, v13·v18까지 동반 하락**했다.
omnibus 한 장에 24항목을 다 걸면 필드 하나가 무관한 항목까지 오염시킨다. **분리가 정면 해법이다.**

각 질문 스키마는 `근거인용`(string)을 **verdict보다 앞에** 둔다 — structured outputs는 스키마 순서대로 디코딩하므로
"인용 → 판단" 순서가 강제되고, 인용이 원문 부분문자열이 아니면 그 사실을 버려 환각을 차단한다(e열 품질도 같이 올라간다).

### S3. 자기일관성 투표 — 핵심 사실만

클러스터 A(9개 항목을 좌우)에만 `n=3~5, temperature=0.7` 다수결. prefill을 공유하므로 **decode만 비용**이다.
표 수를 융합 신호로 쓴다: `rx=0 & llm 5/5 → 1`, `3/5 → 보류`. 지금의 `rx/llm/or/and` 4택보다 결이 고운 결정이 가능하다.

### S4. 재현율 그물 — 좁힌 정규식을 되돌린다

오탐을 잡기 위해 좁혀 둔 정규식들(`ONLY_RE`, `COMPETITIVE_EXEMPT_RE`, `note_ok`, v19의 4중 조건 등)은
F1/2 정리로 다시 재야 한다. 넓은 후보 그물로 뽑고 **후보마다 LLM 짧은 질문**으로 거른다.
특히 dev에서 `rx = 0.000`인 **v1·v9·v19는 LLM이 유일한 탐지 경로**다 — 이 세 항목은 놓치면 항목당 0.042가 통째로 날아간다.

### S5. 부재탐지 5항목 전수 탐색 — 정탐을 잃지 않는 정밀도 이득

v10·v11·v16·v18·v20은 "있어야 할 기재가 없음"이 위반이다. 즉 **우리가 못 찾으면 그게 곧 오탐**이다.
원문 전체에 대해 "이 기재가 어디에든 있는가? 있으면 그 줄을 그대로 인용" 질문을 돌려 **있으면 위반을 취소**한다.
원문에 실제로 없는 건은 아무리 찾아도 안 나오므로 **정탐은 줄지 않는다.** 이 5항목은 배점의 21%이고
v16+v18만 20,000건 중 1,019건으로 양성이 가장 많다.

### S6. 세부품명 매칭 강화 — 9개 항목의 공통 입력

지금은 bigram 유사도로 후보 8개. 615개 중 맞는 품명이 후보에 없으면 v10·v11·v13이 통째로 틀리고
v14~v18도 반대로 오발동한다(`comp` 분기).

- 후보를 **8개 → 30개**로 늘린다(컨텍스트 여유 충분).

## 8. 확인되지 않은 것 (전부 가설이다)

- 서버의 prefill/decode 처리율(8k / 1.4k tok/s)은 **역산 추정치**다. S0의 실측 보정이 없으면 2시간 초과 위험이 실재한다.
- vLLM 0.26의 프리픽스 캐시가 **hybrid(sliding+full) KV에서 기대대로 공유되는지** 확인하지 않았다. 공유가 안 되면 S2 비용이 질문 수만큼 곱으로 늘어난다 → S0가 이 경우 단계를 잘라내야 한다.
- 원문 전체를 넣으면 보일러플레이트(계약이행실적 증명서 서류 목록 등) 때문에 오탐이 늘 수 있다. F1/2 정리상 어느 정도는 감수할 수 있지만 규모는 미측정이다.
- 로컬 4bit와 서버 int8의 장문 처리 품질 차이는 미측정이다. 로컬 결과가 서버를 과소평가할 수 있다.
- 재현율 0.58 추정은 macro F1과 micro 정밀도를 섞은 거친 값이다.

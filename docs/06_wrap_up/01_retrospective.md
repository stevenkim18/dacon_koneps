## 3. 최종 구조

```text
공고 1건 ─┬─ LLM(고정 Gemma 4 26B-A4B, vLLM) ── 사실만 JSON으로 추출
          │    본 호출 · 용역 품목 · 물품 모델명(v9)+보조 · 기업규모·직생 전용 · 지역 전용
          ├─ 정규식 ─────────────────────────── 같은 사실을 원문에서 한 번 더(LLM 결손 보완)
          └─ meta(금액·계약유형 등)
                      ↓
          Python 법령 판정기(법령패키지 조건식) → v1~v24 + 원문 근거 문구 → submission.csv
```

- 서버 실행 55분 42초(제한 120분). 시간 예산 관리자가 100분을 넘길 것 같으면 뒤 단계를 건너뛴다.
- 법령 RAG(임베딩 검색)는 쓰지 않았다. 코드 공유 게시판의 운영진 베이스라인 두 개(Gemma, Gemma + 법령 RAG)는 09-23 기준 약 0.21 수준이었고([09-23 ①](../05_study_log/20260923/1.%20leaderboard_gap_and_cloud_int8_plan.md)), 우리는 법령 조건을 코드로 옮기는 쪽을 택했다. 우리 구조 안에서 RAG를 직접 비교한 실험은 없다.

## 6. 배운 것 — 다음 대회에 가져갈 것

1. **라벨이 어떻게 만들어졌는지부터 본다.** 이 대회의 진짜 문제 정의는 두 발견이었다. dev 라벨은 법 조문을 기계적으로 적용한 결과였고(09-17), 위반 공고는 실제 공고를 고쳐 만든 것이었다(09-23). 둘 다 더 일찍 찾았다면 시간을 아낄 수 있었다.
2. **평가 지표를 수식으로 풀어 채택 규칙을 만든다.** macro F1에서 F1/2 문턱이 나왔고, 이 규칙이 '정밀도가 떨어지면 기각'이라는 직관을 뒤집었다.
3. **검증 도구가 무엇을 못 재는지 안다.** 우리가 양성이라고 한 것만 사람이 검토하면 정밀도만 잰다. 정탐을 꺼도 목록에서 사라질 뿐이라 재현율 손실이 안 보인다(09-20까지 누락을 한 건도 재지 않았다, [09-20 ①](../05_study_log/20260920/1.%20cv_no_longer_predicts_public.md)).
4. **설계에 쓴 시험 문장은 재현율을 부풀린다.** '탐침 재현율 90~100%'는 이미 본 문장에 대한 숫자였다. 규칙을 고치기 전에 새 문장 세트를 따로 써 두니 v1이 0/120으로 드러났다([09-28 ②](../05_study_log/20260928/2.%20fresh_holdout_r18.md)).
5. **로컬과 서버는 다르다.** 로컬 MLX 4bit와 서버 vLLM int8은 출력 형식도, 켜는 항목 수도 달랐다(int8이 v1을 약 3배, v9를 약 2.4배 더 켠다, [09-24 ④](../05_study_log/20260924/4.%20sme_sentence_join_and_v17_private.md)). 판단이 걸린 변경은 서버와 같은 환경에서 잰다.
6. **예측은 낙관적으로 치우친다.** 제출 전 예상 10번 중 범위 위로 벗어난 것은 1번뿐이었다. 구간의 중앙보다 하단 1/3을 기대값으로 본다.
7. **대회 중에 계속 커밋한다.** 이번에는 대회 기간(09-15~09-29) 동안 커밋을 하지 않았고, 저장소의 커밋 18개는 모두 대회 종료 후인 09-30에 한꺼번에 만든 것이다(`git log`로 확인). 그래서 제출 후보·모델 출력·스크립트가 언제 어떻게 바뀌었는지 git 이력으로 복원할 수 없고, 날짜별 변경은 연구 일지와 파일 시간에 의존해야 했다. 다음 대회에서는 아래처럼 한다.
   - 실험 하나(가설 하나)가 끝날 때마다 커밋한다. 제출 직전에는 제출한 `script.py`·`submit.zip`을 커밋하고, 점수가 나오면 점수를 커밋 메시지나 기록에 남긴다.
   - 되돌릴 수 있어야 하는 변경(규칙 수정, 프롬프트 변경) 전에 커밋한다. 실험이 실패해도 직전 상태로 돌아갈 수 있다.
   - 제출한 후보는 태그(예: `sub-0929-r18`)로 표시해, 리더보드 점수와 코드가 어느 시점인지 바로 연결한다.
   - 큰 출력물(`runs/`)은 처음부터 커밋 대상인지 `.gitignore`로 제외할지 정한다.

## 7. 다르게 했다면

- **서버급 GPU 환경을 첫 주에 확보한다.** 로컬(M1 Max 32GiB)로는 서버 int8을 재현할 수 없었고, 클라우드 측정은 09-23에야 했다.
- **dev의 구성(위반 공고 91건 + 위반이 거의 없는 5월 공고 109건)을 먼저 분석한다.** dev 오탐의 대부분(int8 34건 중 24건)이 5월 묶음에 있다는 것을 09-23에야 알았다. 이 묶음은 법상 위반처럼 보여도 라벨이 0인 공고가 있어 라벨이 느슨해 보인다(우리 해석, 운영진 확인 없음).
- **첫날부터 커밋을 습관으로 한다.** 위 6-7번 참고. 커밋 이력이 있었다면 '어느 변경이 점수를 올렸는지'를 코드 차이로 대조할 수 있었다.
- **누락을 재는 도구와 보류 문장 세트를 처음부터 둔다.** 둘 다 대회 후반에 만들었다.
- **상위권과의 격차는 설계 차이였다.** 09-23 밤 기준 1위는 0.7832였고, 제출 1회로 0.739를 낸 팀도 있었다. 최종 1위는 0.78377, 15위는 0.76217이다. 규칙 미세조정으로 닿을 거리가 아니었는데, 상위 팀의 방법은 공개되지 않아 무엇이 달랐는지는 모른다.

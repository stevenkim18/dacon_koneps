# 무라벨 20,000건 분석

> 분석일: 2026-09-16 KST  
> 대상: `open/train_unlabeled.jsonl.gz`  
> 비교 대상: `open/dev.jsonl.gz`  
> 재현 명령: `python3 scripts/analyze_train_unlabeled.py`

## 1. 결론

무라벨 20,000건은 ID와 문서 본문의 기본 무결성이 양호하고, dev 200건보다 실제 활용 범위가 넓다. 다만 라벨이 없으므로 위반 비율이나 항목별 양성 수는 이 분석만으로 알 수 없다.

모델 개선 관점에서 가장 중요한 결과는 다음과 같다.

- 20,000개 ID는 모두 고유하고 빈 문서는 없다.
- 총 문서는 38,862개이며, 15,276건(76.4%)에 첨부가 있다.
- 공고 한 건의 전체 본문 길이는 중앙값 13,782자, 90백분위 32,673자다.
- 공식 베이스라인의 `build_context(max_chars=4000)`은 전체 330,519,537자 중 23.5%만 보존한다.
- 첨부가 있는 15,276건 중 첨부 일부라도 4,000자 입력에 들어가는 공고는 146건(1.0%)뿐이다. 나머지 15,130건(99.0%)은 첨부가 전혀 들어가지 않는다.
- 첨부 의존성이 큰 `모델·상표 명시` 후보 문구는 851건 중 96건(11.3%)에서만 현재 입력에 남는다. `실적 제한` 후보 문구도 4,265건 중 917건(21.5%)만 남는다.
- dev는 제한경쟁과 협상 방식이 무라벨 데이터보다 훨씬 많고, 수의계약은 훨씬 적다. dev 점수만으로 전체 데이터 성능을 추정하면 편향될 수 있다.
- 서로 다른 ID지만 문서와 메타데이터가 완전히 같은 레코드가 14개 더 있다. 자가 라벨링 데이터를 학습용과 검증용으로 나눌 때 같은 중복 그룹을 서로 다른 편에 두면 누수가 생긴다.

따라서 20,000건을 곧바로 전량 자가 라벨링하기보다, 먼저 **중복을 묶고, 메타데이터와 후보 문구로 층화 표본을 만들고, 공고문과 첨부를 모두 볼 수 있는 입력 구성을 검증하는 것**이 안전하다.

## 2. 분석 범위와 해석 기준

이번 분석은 모델 추론과 외부 데이터를 사용하지 않고 다음을 확인했다.

1. 레코드 수, ID 중복, 빈 문서, 조립 버전
2. 공고당 문서 수와 문서 종류별 길이
3. 첨부 탈락과 `input_completeness`
4. 주요 메타데이터, 금액, 날짜 분포
5. 공식 베이스라인 4,000자 입력의 문서 보존율
6. 자가 라벨링 후보 문구의 출현과 4,000자 입력 내 잔존 여부
7. 완전 중복 레코드와 완전 중복 문서
8. dev 200건과 무라벨 20,000건의 구조 차이

후보 문구 집계는 위반 라벨이 아니다. 예를 들어 `현장설명회`가 등장해도 참석업체로 입찰 참가를 제한했는지와 공고기간 조건을 별도로 확인해야 한다. `중소기업`이나 `소기업`도 적법한 제한에서 흔히 등장한다.

실제 모델의 토크나이저가 수행하는 `fit_to_budget`은 실행하지 않았다. 따라서 4,000자 분석은 토큰 예산 적용 전 상한이며, 실제 모델 입력에서는 더 줄어들 수 있다.

- `물품공급 확약`은 82건으로 상대적으로 드물다. 전량 또는 높은 비율을 사람이 검토할 수 있는 현실적인 후보군이다.

## 11. 자가 라벨링 시작 방법

20,000건 전량을 먼저 처리하기보다 다음 순서가 적절하다.

### 1단계: 300~500건의 층화 검증 표본

다음 축을 함께 사용해 표본을 만든다.

- 계약법: 국가계약법 / 지방계약법
- 업무: 일반용역 / 물품
- 계약방법: 수의 / 제한 / 일반 / 지명
- 금액 구간: 1억 미만 / 1억 이상 / 고시금액 경계
- 문서 완전성: 완전관측 / 일부 탈락
- 첨부 종류: 규격서 / 과업지시서 / 제안요청서 / 다중 첨부
- 후보 문구: 각 항목군의 양성 후보 / 문구가 없는 대조군

무작위 표본만 뽑으면 `물품공급 확약`처럼 드문 신호와 항목별 경계 사례가 거의 들어오지 않을 수 있다.

### 2단계: 중복 그룹 고정

완전 중복 레코드와 높은 유사도의 공통 문서를 그룹화하고, 같은 그룹은 학습용과 검증용 중 한쪽에만 둔다. 그렇지 않으면 사실상 같은 텍스트를 본 뒤 검증하게 되어 성능이 부풀려진다.

### 3단계: 입력 구성 비교

dev와 층화 표본에서 다음 입력을 같은 모델 설정으로 비교한다.

1. 공식 4,000자 선두 입력
2. 문서 종류별 최소 예산 배분
3. 각 문서의 앞부분과 뒷부분 보존
4. 항목별 키워드 주변 문단 추출
5. 공고문·첨부 검색 결과를 항목 묶음별로 제공

먼저 후보 문구 잔존율과 근거 부분문자열 보존율을 확인하고, 그다음 항목별 F1과 처리시간을 비교한다.

### 4단계: 불확실한 라벨 분리

일부 문서가 탈락했거나 금액이 0원·1원인 공고, 본문과 메타가 충돌하는 공고는 `확실한 0/1`과 구분한다. 강제로 0 또는 1을 붙여 사례집에 넣으면 부재탐지와 금액 경계 규칙이 왜곡될 수 있다.

## 12. 구현 우선순위

1. `build_context`가 첨부를 통째로 버리지 않도록 문서별 예산을 배분한다.
2. v9, v22, v23과 실적제한 항목군부터 키워드 주변 원문을 추출한다.
3. 중복 그룹을 고려한 300~500건 층화 검증셋을 만든다.
4. 후보 문구가 희소한 `물품공급 확약` 82건부터 수작업 또는 모델 보조 라벨링을 시도한다.
5. 전체 자가 라벨링은 입력 구성과 검증 절차가 안정된 뒤 진행한다.
